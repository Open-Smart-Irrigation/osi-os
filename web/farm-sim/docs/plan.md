This document defines a browser farming game that teaches irrigation and exercises the real OSI decision and automation code. It fixes the architecture, the first milestone (M1, a vertical slice) and the work, tests and gates needed to merge M1. Evidence: [`research/`](research/) holds seven dated research reports and a cross-check (snapshots, not maintained); [`research/evidence/`](research/evidence/) holds the evidence script that runs this plan's farm recipe against the simulator, and its output.

## 1. What the game is

The player runs a smallholder farm in a fictional semi-arid region with two rainy seasons. Water is the scarce resource, and moving it is the main labour cost. Four tiers of OSI help exist: soil readings, a water-balance verdict, a phone-controlled valve and a daily automatic trigger. The phone in the game runs the **real OSI OS edge React app** against the OSI OS simulator on `main` (added by PR #658), and every recommendation or automated action the player sees comes from OSI code.

The same build is a research instrument. Runs are reproducible from a save (replay header, command log and terminal cursor), and the game writes a local event log that the player can export as a file. Version 1 sends nothing over the network.

### 1.1 Relation to existing games

The request named a well-known farming game as the reference for look and mechanics. This project builds an **original** top-down pixel-art farming game in that genre. It uses genre mechanics (tilling, planting, watering, harvesting, energy, day cycle) and aims at the same quality bar of hand-placed pixels and lively animation. It does not copy that game's name, characters, sprites, palette, map layouts, UI frames, item names, festivals or music, and it uses no downloaded or third-party sprite packs. Section 8.1 lists the guardrails.

### 1.2 Goals and non-goals for M1

M1 proves one closed loop in a playable slice, at one OSI tier per run:

1. Game weather and soil physics produce sensor uplinks.
2. Real OSI code (simulator ports and edge modules) reads them and decides or actuates.
3. Water that OSI releases reaches the game soil, and the plants respond.

M1 does **not** include: an economy or tier purchases, NPCs, a neighbour comparison, more than one crop, changing tier during a run, research modes beyond the local log, localisation of game text beyond English, audio, colour-grading LUTs, heat haze, a PWA install, or snapshot-based saves (section 14).

## 4. Architecture

### 4.1 Realms and data flow

```
game window (one JS realm, main thread)
  input ──► command queue ──► core (pure TS, fixed step, seeded PRNG)
                                ├─ world: weather, soil columns, crop, water stores, labour
                                ├─ osi/adapter ──► Simulator (web/react-gui/demo/model.ts, public mode)
                                │      ▲ readingSource(device, at, synthetic)  pulls soil state at each uplink
                                │      ▲ weatherSource(date, zone, now)        game weather + OSI fao56Et0
                                │      └─ outcomes ledger ──► water tap ──► soil and tank
                                └─ log, replay
  view (Pixi) and ui (Preact) read a frozen view model once per render frame; they never mutate core or advance time
  phone iframe (same origin, lazy) ── sync bridge, structured clone, allow-list ──► the same Simulator
```

The Simulator lives in the game realm. Its model bundle pulls in no npm packages (`research/tech.md` 1.1) and the port tests run it under Node, so headless tests and replays run the full OSI loop without React. <!-- slop-allow: "realm" is the ECMAScript term for a JS global environment -->

### 4.2 Timeline, stepping and ordering

**One timeline.** Game time is `sim.now` (milliseconds since the epoch). The core keeps no second clock. A tick is 50 ms of real time; each tick advances game time by `50 ms x pace`, with pace 150 by default (1 real second = 2.5 game minutes, so 06:00-21:00 takes 6 real minutes) [tune]. Pace 300 and 75 are facilitator options. The plan says **tick** for this 50 ms logic step and **render frame** for one draw (30 or 60 per second, 8.4); a render frame runs zero or more ticks (tick order, below).

**Stepping.** The core advances the simulator only through these two functions:

```ts
function drainNow() {                                   // settle everything due at exactly sim.now
  do {
    sim.advanceTo(sim.now);                             // simulator events with atMs <= now (clock.ts:51-66)
    world.stepTo(sim.now);                              // commit the world's grid steps up to now (below)
    world.applyDueTankEvents(sim.now);                  // scheduled tank events (pump completions) due now, in (time, seq) order;
                                                        // each first settles valve flow up to now from the tap's ledger
    water.afterStep(sim.now);                           // drain outcomes; recompute the cutoff from the tank level; may send a due CLOSE
  } while (water.sentCloseThisPass());
}
function advanceOsi(target: number) {
  drainNow();
  while (sim.now < target) {
    const step = Math.min(target,
      sim.clock.nextEventAt(target - sim.now) ?? target,                  // meaningful events only (clock.ts:68-78)
      water.nextCutoffAt() ?? target,                                      // dry-run CLOSE time, 4.4
      world.nextTankEventAt() ?? target,                                   // scheduled pump completions
      nextLocalMidnight(sim.now));
    sim.advanceTo(step);
    drainNow();
  }
}
```

In `src/core/osi/stepping.ts` the loop runs the first pass of that `drainNow()` inline, without its leading `sim.advanceTo(sim.now)`, which would repeat the step's own `sim.advanceTo` at the same instant. That call does nothing: the step's `clock.advanceTo` (`clock.ts:51-66`) has already run every event due by that instant, and the environment refresh finds each zone's key unchanged. A pass that sent a CLOSE still calls `drainNow()`. `tests/integration/repeated-advance.test.ts` checks the no-op at uplinks, a plan start, valve runs, local midnight and the 06:00 trigger.

Valve ACKs, closes, plan starts and the 06:00 trigger are meaningful events, so the loop stops at each and the water tap sees every valve state change at its simulated instant. It also stops at the next cutoff send time, at the next scheduled tank event and at every local midnight: `sim.advanceTo` refreshes completed environment records after each call (`demo/model.ts`, `refreshCompletedEnvironmentRecords`), so the daily refresh, and the capture stamps it writes, always happen at 00:00 whatever the host's call pattern (evidence C19). The game never calls `advance()` or `reset()` on the simulator.

**World stepping.** `world.stepTo(t)` commits the world's physics steps on the canonical grid (6.3) up to `t`. It is idempotent and monotonic (a call at or before the last committed instant does nothing), and by 6.3 the committed state does not depend on how the calls are spaced. It has two callers. The reading callback calls it at its sample instant before answering (4.3): sample events are not meaningful (`scheduleSample` in `demo/model.ts` schedules them with `meaningful: false`, which `clock.ts:72-77` skips), so `advanceOsi` does not stop at them and they run inside `sim.advanceTo`. The stepping functions call it after every `sim.advanceTo` and before the scheduled tank events, so time moves the world with no device registered (T0) and during a sleep. Each step takes its valve water from `litersBetween(zone, stepStart, stepEnd).delivered`, which the tap computes from the last settled tank level, so `stepTo` needs no tank event of the same instant. The view reads the world through the 6.3 query (committed state integrated to the current instant, never stored) and never calls `stepTo`.

**Ordering contract.** Every command, whether a player action, a phone write or raising or lowering the phone, enters one queue in arrival order. One dispatcher, `dispatch(cmd)`, takes commands from the head of that queue: it assigns the command's `seq`, applies it synchronously at the current `sim.now`, appends `{tick, seq, cmd}` to the log, and calls `drainNow()` before returning. Because `seq` is assigned at dispatch and the queue is first in, first out, `seq` order is arrival order. A phone write needs its answer at once, so the bridge first dispatches every command already queued, in arrival order and each followed by `drainNow()`, then dispatches the write and answers. Player actions that take game time (pumping, walking to the well) start at dispatch and progress through world steps. A phone GET is not a command. After `drainNow()` no event is due at `sim.now`, so the `clock.advanceTo(now)` that `requestResponse` runs before dispatch is a no-op on reads. Without it, a one-time plan saved with `fire_at` up to 10 minutes in the past is scheduled at exactly `now` (`demo/model/plans.ts:207-221`) and would fire inside the next phone GET. Evidence C15 creates such a plan: it is dispatched at the write's own instant and the valve opens 2 s later (the one-time ACK delay), with and without an immediate GET, and both runs hash the same.

**Tick order** (normative; 4.8 builds on it). The loop calls `Run.step(realMs)` once per render frame with the real time since the previous call. `step`:

1. dispatches every command still queued, in arrival order, at the current tick value, each followed by `drainNow()`;
2. if paused, stops here: a paused `step` still dispatches queued commands but adds no real time;
3. otherwise adds `realMs` to an accumulator and runs `floor(acc / 50 ms)` ticks, at most 8 per call, taking 50 ms from the accumulator per tick. Real time beyond the cap (a catch-up limit) is dropped, never replayed, and logged as a `slow_frame` event (7.6), which is not a command and is not hashed;
4. in each tick, runs `advanceOsi(sim.now + 50 ms x pace)`, adds 1 to the tick counter and, if the counter is now a multiple of 600, records the checkpoint hash.

Input queued between ticks is dispatched before the next tick, at the then-current tick value. A phone write also arrives between ticks; the bridge dispatches the queue ahead of it and then the write (ordering contract), so a player action queued earlier in the same render frame is logged and applied before the write. Rendering reads the view model once per render frame, after `step` returns, and never advances time. A log record `{tick, seq, cmd}` therefore means: dispatched when the counter equals `tick`, before the next advance. World physics advances only through `world.stepTo`, on its canonical grid (6.3); sensor values are pulled inside the simulator's sample events (4.3).

**Tank events.** The tank level changes at a dispatched pour or fill (applied by the dispatcher at `sim.now`, then `drainNow()`), at a scheduled pump completion, and continuously by valve flow. The 05:00 event restores the well's daily yield (6.5) and does not change the tank. Order at one instant: simulator events, then `world.stepTo` to that instant, then scheduled tank events (pump completions), then the cutoff recomputed from the resulting level and a due CLOSE sent. A pour or fill is dispatched later, after the advance that reached the instant has run its drain; a pour or fill dispatched at an instant whose drain already sent a CLOSE therefore leaves that CLOSE in flight. A CLOSE already sent is never withdrawn; a tank event during its 2 s flight changes only how much of that flight is delivered (evidence C23, whose refill at the send instant is a scheduled pump completion). A natural close and a cutoff close at the same instant are both priority 1: the natural close is a timed open's closure (`demo/model/irrigation.ts:60`) or a weekly plan's close, which the plan start schedules before any cutoff CLOSE is sent (`demo/model/plans.ts:257-260`); the cutoff's close is the manual-close event (`irrigation.ts:108`). The natural close was scheduled first and runs first (`clock.ts:55` sorts by time, priority, then sequence), so the run ends `COMPLETED`; closing invalidates the actuation generation (`irrigation.ts:73`), so the clock drops the cutoff's close as stale without running it (`clock.ts:62`). Evidence C24 shows this for a timed open; the 11.2 Cutoff tests add the weekly-plan tie. The log records which close ended the run.

Sleeping records one command. Behind the fade, the game advances to 05:50 local across animation frames. It yields at OSI event boundaries or on the 10-minute soil grid and holds player input until the advance finishes. Replay runs the same night synchronously. The player wakes 10 game minutes before the 06:00 trigger, four real seconds at the default pace.

**Pause.** Raising and lowering the phone are always commands (`phoneOpen`, `phoneClose`); with "pause while phone open" on (default), `step` runs no tick between them and drops their real time. The tick counter and simulator time at any point are therefore a pure function of the save (header, log and cursor, 4.8). Phone writes still dispatch at the frozen instant; a valve command therefore stays pending in the phone until the player lowers it (its ACK is 2 simulated seconds away), and the T3 tutorial says so (7.4).

With a reading source, the hook takes one creation uplink from the source when a device is registered, so `latest_data` never shows fixture values (section 9; evidence C8).

### 4.4 Water out: tap, ledgers and dry-run cutoff

**Water tap.** `litersBetween(zone, from, to)` integrates each run in the outcomes ledger from `observedOpenAt` to `observedCloseAt`. The rate is the active command's `flow_rate_lpm` while the run is active, because the outcome's `flowRateLpm` is null until the first flow integration (`demo/model/irrigation.ts:37-46`); after close it is the outcome's `flowRateLpm`. This equals the simulator's own integration (`demo/model.ts:463-472`; evidence C3, C4). `drain()` emits `commanded`, `opened` and `closed` events with simulated timestamps for animation, the HUD and the log.

**Two ledgers.** The tap keeps `estimated` litres (what the simulator counts and the phone shows as metered) and `delivered` litres (what left the tank, clamped by the tank level). Soil physics uses `delivered`.

**Constant flow.** The drip line on bed A runs at a constant 8 L/min while the tank holds water; the valve's `flow_rate_lpm` is set to 8 by the farm builder, so `estimated` equals `delivered` while water is available.

**Dry-run cutoff.** The world has a dry-run switch on the tank outlet (a game device, named in the log and the info panel). Public mode closes a valve 2 s after a CLOSE command (`demo/model/irrigation.ts:105-108`), so the tap sends `POST /api/valve/:eui {action: 'CLOSE'}` at:

- for a command that has not opened yet: `ACK time + tank / rate - 2 s`, not before now. A trigger or manual open is seen when commanded, 2 s before its ACK, so an empty tank closes the valve before it opens and nothing is counted (evidence C11). The close and the ACK land at the same instant; the close has priority 1 and the ACK priority 3 (`irrigation.ts:57,108`), so the close wins.
- for a running command: `now + tank / rate - 2 s`, not before now (evidence C3, C4).

The only remaining difference is a run that meets less than 2 s of water after it opened: a weekly-plan start, which opens with no delay (`plans.ts:254`), or a running valve whose tank the player empties by filling a can or jerrycan from the tank tap. `estimated` then exceeds `delivered` by at most `2 s x 8 L/min = 0.27 L` (evidence C12 for a weekly-plan start: 0.27 L counted, 0.15 L delivered; the can-fill case is an 11.2 Cutoff test). A one-time plan opens 2 s after dispatch, so the pending-command rule applies and its count is exact (evidence C18). The log's `cutoff` event records both numbers. The phone shows such a run as cancelled; the info panel names the dry-run switch.

**Meter day.** Litres a meter reports belong to the day of the uplink that reports them, as on a gateway: a run from 23:55 to 00:05 shows 40 L on the new day's phone counter at the 00:00 uplink, while the world's slice report attributes litres by delivery time (40 L to each day). The two totals agree over both days (evidence C22); the info panel explains the difference for runs that cross midnight, and the phone labels metered irrigation as coming from a simulated flow meter (4.5).

Watering-can water is applied by hand and is never metered, as on a real farm. Manual-tap water (T0-T2, before a valve exists) passes the flow meter at T2 and reaches OSI through `flow_liters_delta` (evidence C2).

The valve service routes `strega/{timed-action,partial-opening,flushing}` change the valve opening outside the actuation ledger (`demo/model/irrigation.ts:202-282`); the bridge refuses them (4.6), so every run is at 100% opening.

### 4.5 Weather and ET0

The hook's weather source is `weatherSource(date, zone, now)`, stored per simulator instance and activated only for the duration of each public simulator call (set on entry, previous value restored on exit), so two live simulators in one realm, nested calls and direct calls to the exported environment helpers do not interfere (section 9). It returns `{et0, rain, maxTemp, meanRhPct, windSpeedMps, et0Source: 'fao56_daily_game_weather', et0Tier: 'fao56_daily', hourlyRainMm}`: <!-- slop-allow: "realm" is the ECMAScript term for a JS global environment -->

- **As-of rule.** A date before today's local date returns that day's actual weather. Today and later dates return the weather service's forecast issued at today's local midnight, with lead `k = date - today` in days. Today's ET0 therefore comes from the lead-0 forecast, which matches the product, where today's ET0 comes from the provider's forecast day (`research/osi-tiers.md` section 2).
- `et0` is computed by `osi-agronomy-daily/et0.js` (`fao56Et0`) from the day's Tmin, Tmax, mean RH, wind at 2 m and solar radiation, elevation 1,200 m and latitude -2.0, rounded to 0.01 mm by the module.
- `rain` and `hourlyRainMm` (24 values, indexed by local wall-clock hour) follow the as-of rule. With a source, the simulator's hourly forecast rows are end-stamped, as the edge treats Open-Meteo hours: a row stamped T carries the rain of the hour ending at T, and the next-24-hour total sums rows with T in (now, now + 24 h], the window of `osi-zone-env` `sumRain` (`index.js:550`). The verdict's forecast input therefore equals the edge's for the same forecast, on the hour and between hours (evidence C9, C16). The summary's hourly rows, which the forecast chart draws, use the same window, so the chart's rain sums to the total (hook test 12). The daily forecast row for today sums the rows ahead of now, including the end-stamped row whose hour began before now. The hourly temperature shape uses the UTC hour of each row (illustrative, below). Measured rain reaches OSI only through the gauge (4.3).
- The source is total: every value is a pure function of (seed, issue date, target date), memoised per pair (a summary asks for about 82 dates), and it returns null for dates outside [generator start, today + 3 days]. The simulator constructor asks for dates before the generator start; those get null, and the builder clears every retained record afterwards (4.7).
- Past-day records are retained when first computed after a day ends (`demo/model/environment.ts:117-120`), and `sim.advanceTo` refreshes completed records (`demo/model.ts:320-330`). Past dates return actuals, so a retained value does not depend on when it was computed. The 11.2 Honesty test checks this with a source whose lead-0 forecast differs from its actuals; evidence C10 shows only that GETs are inert, because its source ignores `now` and returns the same values as forecast and actuals (`research/evidence/plan-claims.ts:77-84`).

9. At T4, apply the scenario's trigger preset if it has one (`PUT /api/irrigation-zones/1/schedule`); otherwise the player sets it in the app.
10. Set `sim.state.sessions.pendingOutboxCount = 0` (canonical pending mutations bump it, `demo/model.ts:707-709,723`).
11. `drainNow()`.

The builder calls `sim.requestResponse` directly, outside the phone allow-list, and its calls are part of the replay initialisation, not the command log.

### 4.8 Determinism and replay

- The replay header is `{format: 1, build, scenario, seed, tier, start, pace, pauseWhilePhoneOpen, moistureLens, hints}`. The facilitator panel sets scenario, tier (from the scenario's tier list), pace, `pauseWhilePhoneOpen`, `moistureLens` and `hints` before a run, and changing any of them restarts the run (7.6); `format` and `build` come from the build, `seed` and `start` from the scenario file (6.6). A run started without the panel uses the first scenario in the scenario list (`baseline`, 6.2), its first listed tier, pace 150, pause while phone open on, moisture lens off and hints on. One function, `createRun(header)`, starts both a new game and a replay.
- Core randomness comes from one sfc32 PRNG with named sub-streams (`weather`, `forecast`, `sensorNoise`, `crop`), each keyed so adding a system does not shift another's sequence; forecast draws are keyed by (issue date, target date).
- Persistent values are quantised at the boundary. Each soil step computes its fluxes (infiltration, drainage, ET, runoff, percolation) from the stored state, rounds each flux to 0.01 mm (integer hundredths, ties away from zero) and applies the rounded fluxes, so layer storage stays a sum of applied rounded fluxes and the per-step balance holds exactly in 0.01 mm units. A nonzero drainage or percolation flux that rounds below 0.01 mm is applied as 0.01 mm, capped at the layer's excess: on the 10-minute grid `excess x 10 min / 6 h` rounds to 0 below 0.18 mm, where an excess would otherwise stall, and with the floor it drains to zero (6.3). kPa and litres are rounded to 0.01, ET0 to 0.01 mm (by `et0.js`).
- The command log holds `{tick, seq, cmd}` records in dispatch order, which is arrival order; `seq` is assigned at dispatch (4.2). One save type, `{header, log, checkpoints, cursor}`, stores them with a terminal cursor `{tick, seq, simNow}`, so two saves with the same last command but different idle tails restore to their own instants. Replay applies the records in log order, each at its `tick`, and advances ticks until the counter equals `cursor.tick` and every record with `seq <= cursor.seq` is applied, then asserts `sim.now === cursor.simNow`. Every 600 ticks the run records a state hash: SHA-256 over the core state and a digest of the simulator, encoded base64.
- The digest covers the simulator's zones (each with its trigger schedule, `zone.schedule`, `demo/model.ts:1283`), devices, outcomes, trigger evaluations, every device's readings and the retained environment records with their provenance, plus the state that allow-listed writes change: valve plans (`sim.state.schedules`), valve settings and plan runtime (`sim.state.valveSettings`, which `scheduler-status`, `plan/resend`, plan writes and `default_open_minutes` change), active commands (`sim.state.activeCommands`; all three `demo/model/state.ts:40-43`) and the ids of pending simulator clock events (`clock.ids()`, `demo/model/clock.ts:49`). Their times are not read: they follow from digested state (command timestamps plus fixed delays, plan fire times, and sample ids, which carry their instants), so the digest uses the public model API only. The 11.2 replay and allow-list tests use this digest. It is a superset of the evidence digest (`research/evidence/plan-claims.ts:301-303`), which leaves out valve settings, active commands and clock events.
- Reads are inert under the ordering contract (4.2) and the builder's record reset (4.7): GETs at arbitrary times, including right after a write, leave the digest unchanged. Evidence C10 and C15 show this on the evidence digest; the 11.2 replay test repeats it on the full digest. `GET /api/valves` creates a valve's plan-runtime entry in `valveSettings` on first access (`demo/model.ts:553-561`, `:1052`), but the builder's settings write (4.7 step 8) creates it first (`irrigation.ts:97`, `demo/model.ts:601`), so no later read adds one. The host's call grid does not matter either, because the loop stops at local midnight (evidence C19).
- The session is fixed (4.6), so the log holds no credentials and no session transitions. Replay acceptance includes a save that ends between two hash checkpoints.
- V8 (Chrome and Node) is the reference engine; other engines can differ in the last bit of `Math.exp`/`Math.pow` inside `et0.js` (`research/tech.md` 1.15), which the quantisation mostly hides.

## 6. World simulation

Values marked [tune] are game balance; the others cite `research/agronomy.md` parameter tables A-D.

### 6.1 Place and calendar

Fictional plateau, latitude -2.0, longitude 0.0, elevation 1,200 m, `Etc/GMT-3`. Seasons follow the bimodal model of `research/agronomy.md` table A with fictional names: Long Rains (Mar-May), Cool Dry (Jun-Sep), Short Rains (Oct-Dec), Hot Dry (Jan-Feb). The M1 slice runs 14 days of Hot Dry from 2027-01-11 06:30 to 2027-01-25 06:30 local.

### 6.2 Weather generator

A first-order Markov wet/dry chain with gamma-distributed amounts per month (table A): January `p01 = 0.129`, `p11 = 0.329`, gamma shape 0.75, scale 10.67 mm, Tmax 29.3 °C, Tmin 15.6 °C, RH 64%, wind 1.54 m/s, Rs 23.3 MJ/m²/day; February from the same table. Daily noise: Tmax SD 1.5 °C, Tmin SD 1.2 °C; wet days -2.0 °C Tmax, +10% RH, Rs x 0.70; dry days Rs x 1.07, RH -3%; RH clamped 15-98%; wind lognormal sigma 0.25. A wet day's rain falls in one burst of 1-3 hours that starts between 01:00 and 19:00 local and so ends by 22:00, with start and length from the `weather` stream [tune]; no burst straddles midnight. The generator starts on 2026-10-11, 92 days before the slice, and runs forward; table A's parameters reproduced about 584 mm/year with CV 0.33 over 2,000 simulated years (`research/agronomy.md` section 1.6).

Forecast for lead k days [tune]: each day's wet/dry state flips with probability `0.1 + 0.1k`. A wet day's amount is multiplied by a lognormal factor with sigma `0.3 + 0.15k`; a dry day forecast as wet gets an amount drawn from the month's gamma distribution. The burst start hour moves by up to `k + 1` hours, staying within 01:00-19:00. All draws come from the `forecast` stream keyed by (issue date, target date).

Three scenarios: `baseline` (one seed), `dry-spell` (a seed whose slice has no rain for at least 7 consecutive days) and `storm` (a seed with one rain day of at least 15 mm). `scripts/find-seeds.ts` picks the seeds and rejects any seed with rain before 06:30 local on day 1, when the gauge registers with a 0 mm creation uplink (4.3, 5.2); the seeds are frozen in `src/scenarios/*.json` with the initial state (6.6).

### 6.3 Soil

Sandy loam (table B): van Genuchten θr 0.039, θs 0.387, α 0.0267/cm, n 1.449; θFC 0.198 (field capacity at 20 kPa), θWP 0.062; TAW 135 mm/m; curve number 88 (row crop, crusted) for rain runoff.

Each bed is a column of five layers: L1 0-10 cm, L2 10-30, L3 30-50, L4 50-70, L5 70-100 cm. The 20 cm and 40 cm probe depths are the centres of L2 and L3. The column steps on a canonical grid that depends only on inputs: every 10 minutes of simulated time from local midnight, plus every instant where an input changes (a valve opens or closes, a rain burst starts or ends, a can or tap pour starts or ends). `world.stepTo(t)` (4.2) commits every grid step up to `t`. Queries at other instants (the game loop) read the state at the last grid point and integrate exactly to the query time without quantising it, so the call pattern of the game loop never changes the stored state. Each grid step:

1. **Infiltration.** Rain reaching the soil and irrigation enter L1 and fill each layer to saturation top-down; water that cannot enter L5 is deep percolation. Rain runoff: the day's runoff fraction comes from the SCS curve-number equation on the day's actual rain total, and each hour's rain infiltrates by `1 - fraction`. Drip irrigation produces no runoff; watering-can water on dry crusted L1 (depletion over 50%) loses 10% [tune].
2. **Drainage.** Water above field capacity in a layer moves to the layer below at rate `excess / 6 h`: a step of length Δt moves `excess x Δt / 6 h`, at least 0.01 mm while an excess remains (4.8), so 98% of an excess drains within 24 h and the rest reaches zero; out of L5 it is deep percolation, counted as lost.
3. **Evapotranspiration**, single crop coefficient (FAO-56 chapter 8): `ETa = Ks x Kc x ET0` for the day, distributed over daylight hours by a sine. Soil evaporation is part of Kc and is not added again. Withdrawal: L1 supplies 10% while its depletion is below TEW (17 mm per FAO-56 for this soil, table B), else 0; the rest is drawn by root-zone quarters with shares 40/30/20/10 (top to bottom), each quarter mapped to layers by depth overlap with the current root depth. A layer at wilting point supplies nothing, and its share moves to the next deeper root layer.
4. **Water stress.** `Ks` from root-zone depletion against `RAW = p x TAW`, with `p = 0.40 + 0.04 (5 - ETc)` clamped to 0.1-0.8.
5. **Tension.** Each layer's depletion fraction `f = (θFC - θ) / (θFC - θWP)` maps to kPa by log-linear interpolation between the positive nodes of the depletion table (f = 0, 0.1 ... 1.0 to 20, 24.8, 31.1, 40.0, 52.8, 72.3, 103.8, 159.6, 271.2, 543.6, 1500 kPa). Above field capacity the filled fraction of drainable water maps linearly in kPa (0.25, 0.5, 0.75, 1.0 to 10.3, 5.5, 2.6, 0 kPa). Results are clamped to 0-1500 kPa.

Unit tests pin mass balance per step (inputs equal storage change plus ET, percolation and runoff, exactly in 0.01 mm units, because each step applies fluxes already rounded to 0.01 mm, 4.8), the drainage time constant and the 0.01 mm floor (11.1), the table nodes including the 0 kPa endpoint, and grid invariance: the same inputs queried at two different call patterns give the same stored state.

Tile colour shows the surface (L1) in five bands with the phone's edges: saturated < 8, wet 8-20, moist 20-50, dry 50-100, very dry > 100 kPa. The surface dries before the 20 cm probe does; the tutorial teaches that lag instead of hiding it.

### 6.4 Crop

Tomato, transplanted, catalogue id `tomato`: Kc 0.60 / 1.15 / 0.70, edge stage lengths 30 / 40 / 45 / 30 days, root depth growing linearly to 1.0 m by the end of development, p 0.40, seasonal Ky 1.05 (FAO-33). The game applies the seasonal Ky to a 7-day window, a simplification marked [tune]. The game's phenology uses the edge stage rows, so OSI's Kc and the game's crop agree.

- Bed A (8 x 8 tiles, 64 m², about 140 plants at 90 x 50 cm): day 5 of the mid stage at the start, root depth 1.0 m; it stays mid-season through the slice.
- Bed B (6 x 4 tiles): empty; the player tills it and transplants seedlings (root depth 0.10 m, initial stage), then waters by can. No sensors.
- Yield: potential 20 t/ha [tune] over the 75 days of mid and late stage. Each day's ripening potential is scaled by `1 - Ky (1 - ETa/ETc)` averaged over the previous 7 days. Ripe fruit accumulates per tile, is picked by the player and rots after 4 days on the plant.
- Stress visuals from Ks: 1.0 upright; 0.8-1.0 midday leaf rolling that recovers overnight; 0.5-0.8 rolling all afternoon and dull grey-green; 0.2-0.5 wilting and flower drop; below 0.2 for 3 days scorch and permanent loss.

### 6.6 Frozen scenario state

Each scenario file freezes the seed, the start, the tier list it supports and the initial state: layer depletion fractions L1-L5 `[0.00, 0.35, 0.30, 0.45, 0.40]` for bed A and `[0.20, 0.40, 0.30, 0.25, 0.20]` for bed B, tank 300 L, well yield 480 L (310 L in `dry-spell`, 6.5), bed A fruit (green 6 and ripening 2, visual cues; ripe 1, one ripe batch), bed B empty, player energy 100 [tune]. Each value sets up a tutorial beat (7.4):

- **Neglect shows inside the slice.** Bed A starts 45.9 mm below field capacity over its 1 m root zone, 3.8 mm short of RAW (49.7 mm at an ETc of 5.8 mm/day). The drier layers are L4 and L5; the probe layers L2 and L3 keep their values. Left unwatered, bed A rolls at midday from day 2 (day 1 in `storm`), turns grey-green by day 8 (day 5 in `storm`) and ends the slice at Ks 0.52-0.67.
- **Bed B's transplants roll on day 2.** Bed B's L1 starts 2.7 mm below field capacity, under the 50% crust threshold (6.3). A seedling transplanted between 08:00 and 14:00 on day 1 and then left dry stays turgid on day 1, rolls on day 2 from between 11:14 and 14:21 until 16:00, and is turgid again after 16:00 (tutorial scenario, checked every minute). Transplanted at 07:30 or earlier, it is grey-green by 17:04 on day 2.
- **The probe answers a drip run.** Bed A's L1 starts at field capacity, so by day 3 it holds only the deficit that two days of uptake leave, and the part of the day-3 tutorial run (60 minutes, 480 L, 6.75 mm net) above that deficit drains into L2. A 45-minute run (5.1 mm net) leaves little above the deficit and moves the 20 cm reading by 2.84 kPa in three hours in the tutorial scenario; that is why the tutorial run is 60 minutes. How far the reading moves still depends on the state the seed has produced by day 3, so the day-3 hint reports the observed change and draws no conclusion from it (7.4).

T0 and T1: tap open 45 minutes at 07:00 on even slice days (day 2, 4, ...). T3: weekly plan, all seven weekdays (mask 127), 07:00, 45 minutes. Both devices sit on that outlet line: from T3 the valve box under the tank tap, and from T2 the flow meter at the header's foot. The probe stands on a drip line next to a plant (tile 14, 7 in `src/core/map.ts`), where the emitters wet the soil: a tension probe between drip lines sits in soil the drip barely reaches and reads dry whatever the farmer does. The soil model wets bed A uniformly, so the placement changes the picture and the lesson, not the readings.

### 7.2 Player actions

Move (8 directions), interact, till, transplant, fill can or jerrycan (tank tap, shared well), pour into the tank, water a tile, pump, open or close the manual tap (T0-T2), harvest a tile, feel the soil (a text answer from L1: "sticky and cool", "crumbly", "dusty"), raise the phone (T1+), sleep (after 18:00, wakes at 05:50).

### 7.3 Interface

Preact DOM overlay at the logical pixel scale: tool belt on the left edge in landscape, water gauge (litres carried) and energy bar, a daylight arc with the day number, the phone raised with a key or a tap, signboard-style dialogue boxes, the "About this screen" panel and the slice report. Tap targets are at least 44 CSS px. Keyboard, mouse and touch (virtual stick plus tap-to-act) in M1.

In portrait the overlay moves off the view. The status bar sits at the top, the view spans the screen width below it, and the tool belt becomes a row under the view; the field notes, action buttons and stick share the bottom of the screen. The view's band, between the status bar and the tool row, takes the height the other rows leave and gives it up first on a short screen, so the bottom row, Sleep included, stays on screen. Portrait keeps whole-number zoom (D8, 8.4) but has a logical view of its own (`portraitViewport` in `src/view/camera.ts`). The scale is the largest whole number, at least 1, at which 15 tiles fit across the band [tune]. At that scale the view is as wide and as tall as the band, rounded down to whole logical pixels, but no taller than the map's 288 px and at least one tile each way; it sits centred at the top of the band. A band 720 device pixels wide or more (zoom 3 and up, such as a 360 px phone at device pixel ratio 2) therefore shows at least 15 and fewer than 20 tiles across. A 412 x 760 phone at ratio 2 gets a view 274 px wide at 3x, 17 tiles, and 281 px tall with the first day's hint showing; a 360 x 740 phone at ratio 3 gets 270 x 288 at 4x. Landscape and desktop keep the 480 x 270 view at the largest whole-number scale that fits, at least 1, centred.

The deep-drying beat does not test the 20 cm reading of two days earlier. A trigger holds its own depth near its threshold, so that reading is often just above it. In 33 headless runs at 25 kPa (each scenario's weather with 11 sensor-noise seeds), testing that reading as well silenced the beat in 10 runs whose 40 cm reading met the drying conditions, 8 of them because that reading stood at 25.2 to 27.3 kPa; without the test, 2 stay silent. Those 2 are real misses, and the beat stays silent in them because its hint would be false: the hint says the 20 cm reading is under the threshold, and on every morning whose 40 cm reading meets the drying conditions that reading is above 25 kPa. In `storm` with noise seed 7 the 40 cm reading climbs from 110 to 156 kPa on days 8 to 10 while the 07:00 20 cm reading stands at 25.05 to 27.01 kPa. In `dry-spell` with the same seed the 40 cm reading goes from 51 kPa on day 8 to 68 kPa on day 10, when the 20 cm reading is 27.57 kPa. The beat also comes late in a third of the runs: 11 of the 33 meet the conditions only on day 10, the last day checked (6 in `baseline`, 3 in `dry-spell`, 2 in `storm`). The hint names the next morning because water takes most of a day to reach 40 cm: on the day of a 90-minute trigger run in `dry-spell` the 40 cm reading stands at 68.5 kPa at 05:00 and 75.3 kPa at 21:00, and falls to 64.5 kPa only by 07:00 the next day. When a headless player raises the duration to 90 minutes on the firing day, the 40 cm reading holds or falls on the morning after the next run (baseline 104.5 to 103.7 kPa, dry-spell 63.6 to 64.5, storm 147.7 to 118.2, against rises of 34, 10 and 10 kPa at 45 minutes), then climbs again on the days the trigger skips. At 60 minutes it still climbs after the next run (baseline 104.5 to 138.0 kPa).

Each hint is capped on its own. The tutorial checks for that plan on entering day 5, right after each plan the phone saves, and after each day-5 uplink. A hint that explains an observation (day-2 leaf rolling, the day-3 probe readings, the day-4 Water tab, the day-6 trigger decision, deep drying on days 8-10) is never skipped. A player who waters, opens the tap and plants on day 1 before being asked therefore still gets the lessons of days 2 to 4. The facilitator panel can turn all hints off.

### 7.5 Slice report

Per day and in total: rain, irrigation litres by source (can, tap, valve), litres lost (runoff, deep percolation), pump strokes and shared-well trips beside the litres, energy and game minutes spent on water, bed A's root-zone water (mm in the top metre) at the start and end, bed A stress days (mean Ks < 0.8; bed B transplants stay out, because the reference runs have none), tomatoes picked and lost, water productivity in kg/m³, and the dry-run cutoffs.

At T4 the report adds two sentences that compare the run's first 14 day records with the scripted daily-timer (T3) reference run of the same scenario. `scripts/update-golden.ts` writes that run's figures, its shared-well trips and stress days included, to `src/scenarios/reference-summary.json` from the goldens' T3 rows. The `baseline` T4 reference run reads: "The soil-triggered valve watered on 6 of the 14 days and the daily timer (reference run, same weather) on 14: about the same tomatoes, 23.36 kg against 23.94 kg, for 43 % of the water and half the pumping. Bed A had 2 stress days against none, and the root zone ended 35 mm drier, about 2,240 L the soil has lent." The first count is the days with valve water. The text names the soil trigger only when at least one valve run opened in those days and the trigger started each of them; otherwise, as after a manual valve run or a plan run, it starts "Your valve watered on N of the 14 days". Both harvests are always printed in kilograms, with "about the same tomatoes" only when they differ by at most 3 % (otherwise "fewer" or "more tomatoes"). A share of litres or pump strokes from 0.45 to 0.55 inclusive is "half"; any other share is the whole percentage, rounded normally ("60 % of the pumping"). Shared-well trips are added when either run made any ("no trips to the shared well against 22"), and stress days when the two runs differ. The root zone ends "the same" within 0.5 mm of the reference; otherwise X mm "drier, about L L the soil has lent" or "wetter, about L L more held in the soil", where L is X in whole mm times bed A's 64 m², rounded to the nearest 10 L. A run without a harvest gets no comparison.

### 7.6 Facilitator panel and log

The panel (key combination or URL flag) sets scenario, tier (from the scenario's tier list), pace, moisture lens, hints and pause-while-phone-open before a run starts, and exports the log. All six are stored in the replay header (4.8), and changing any of them restarts the run. A run started without the panel takes the defaults of 4.8.

The log is JSON Lines. `src/core/log.ts` writes only deterministic fields: `seq`, `sim_time`, `type`, `payload`. `src/ui/export.ts`, outside `core/`, stamps each new record with the wall-clock time when the loop receives it after `step` returns; at export it adds `wall_offset_s` (seconds since session start), `session_id` (random per export), and `scenario`, `seed`, `build` and `tier` from the replay header. When a replay is loaded, `src/ui/export.ts` stamps the records the load rebuilt with the load time and writes a `replay_load` record after them, without a `seq`, whose `last_replayed_seq` names the last rebuilt record. M1 event types: `session_start`, `command`, `phone_request`, `phone_refused`, `api_read`, `irrigation`, `cutoff`, `trigger_evaluation` (copied from `sim.state.triggerEvaluations`), `world_daily`, `harvest`, `report`, `slow_frame` (real time dropped by the catch-up cap, 4.2). Like `api_read`, `slow_frame` is not a command and stays out of the command log and the checkpoint hash. Export is a file download; nothing is sent. A hash chain and the research consent flow come with M4.

## 8. Art and rendering

### 8.1 Originality guardrails

- References are the real world (soil, plants, buildings, light), described in words; no reference board from any game.
- No wooden-plank UI frames, parchment dialogs, heart meters, gem currency or festival calendar; the UI style is a painted signboard (`research/art-direction.md` 1.10).
- The 46-colour palette was picked for this setting (`research/art-direction.md` 1.4).
- Devices are generic shapes, not reproductions of commercial products.
- Cloth patterns come from a small geometric grammar, never a named design.
- Every sprite is a TypeScript module of palette-keyed strings or a seeded generator.

### 8.2 Look

"Red earth, gold grass, blue hills": laterite is the base ground colour, green appears with water, and water blue is reserved for water and wet sheen. Midday light is near vertical with blob shadows; golden hours have long, sun-sheared shadows (`research/art-direction.md` 1.1-1.2, 1.8). Warm light hardly shows on orange ground, so dusk puts its colour into the shade and the long shadows, which are violet; by half an hour before sunset the light is about a fifth below noon, and water keeps its blue. Dawn stays cooler and paler than dusk. Foliage that should stay green uses the foliage keys: at dawn and dusk the near-grey `P` takes the cool shade colour and turns slate.

### 8.3 Sprite source and bake

- Format: `sprite({id, size, anchor, rows})` with palette keys, `derive(src, {remap, mirror, shiftRamp, overlay})`, `compose(layers)` and `variants(src, seed, n, op)` (`research/art-direction.md` 3.1); a validator checks row widths, palette keys, anchors and colour budgets.
- Generators: ground variants, crack overlays, grass tufts, corner-based dual-grid autotiles for tilled soil and paths, blob-47 autotiles for the hedge.
- Bake: `scripts/bake-atlas.ts` (Node, a minimal PNG encoder over `node:zlib`) rasterises the generated sprites. The terrain generator remaps colours for wetness bands. The crop generator changes posture and colour for stress and sway. The bake script also makes a one-colour mask of every frame that casts a long shadow (the view tints it with the colour of the hour), packs 2048² pages with 1 px gutters, and writes `atlas-<hash>.png`, `atlas.json` and the pixel font into the untracked `public/generated/` directory. A test pins the atlas hash.

### 8.4 Render pipeline (M1: four passes)

1. World into a RenderTexture of the logical view plus a one-tile margin (496 x 286 for the 480 x 270 landscape view; it resizes with the portrait view of 7.3, as do the light buffer and the composite): terrain chunks (32 x 32 tiles, re-baked when a tile changes), a multiply shadow layer (blob shadows and sun-sheared silhouettes), y-sorted sprites, rain and splash particles.
2. Light buffer: additive light sprites (lamp, LEDs, phone glow).
3. Composite: `albedo x (ambient(time) + lights)`, where ambient interpolates four keyframe colours (dawn, noon, dusk, night).
4. Nearest-neighbour integer upscale with the camera's sub-pixel remainder applied as a screen offset.

Rules: integer zoom only, in portrait too (7.3); sprites, tiles and particles at integer logical positions; no rotation except 90°; no bilinear sampling of sprite textures; sway is baked frames. Two quality tiers from `deviceMemory` and a 2 s render-frame probe: low (at most 30 render frames per second, 150 particles) and standard (60, 400 particles). The render rate does not change game speed: ticks follow real time (4.2).

GPU time under SwiftShader is not meaningful, so CI gates only CPU-side metrics, with a 2x margin.

`tests/e2e/perf.spec.ts` runs the workload against the built game (`index.html?facilitator&perf`) in a 412 x 760 phone viewport, at the CPU throttle in `FARM_SIM_PERF_CPU_THROTTLE` (1 to 6, default 6), and writes the table to `perf-<rate>x.json` in `FARM_SIM_E2E_ARTIFACTS`, or in the test's output directory when that is unset. `?perf` loads the probe in `src/render-review.ts`. From outside `src/core`, it wraps `FarmRun.step` (`core.step`), `FarmOsiAdapter.advance` (`osi.advance`), `FarmRun.viewModel` (`view.sync`), `renderer.render` and `FarmRun.load`, and a hook in `src/loop.ts` gives it each render frame's span; without `?perf` none of this loads. `playwright.config.ts` runs the spec in its own project after the other specs, so `npm run test:e2e` includes it and no second worker shares the CPU; `npm run test:perf` runs it alone. At every rate the spec asserts the CI-gate column, and it fails when the probe recorded too few frames, ticks or uplinks, or not exactly one sleep jump and one replay load. Its browserless test reads the table above and fails when a budget or gate in `ROWS` (`scripts/check-perf.mjs`) differs from it. `scripts/check-perf.mjs <directory>` prints the 1x, 4x and 6x table for 11.4 from the JSON files.

Render frames count in play windows with the phone lowered. During the sleep advance, the game holds the last rendered frame. The core tick average divides `core.step` time in those frames by their ticks. An OSI step crosses an uplink when the soil probe's latest sample changes during one `osi.advance` call; the p95 also takes the steps of an untimed fast-forward from late morning to 21:00, about 29 crossings in all. Sleep latency runs from the start of the first slice to the end of the last, including time between frames. A long task counts when it starts in a play window, including any task that runs a sleep slice. On failure the table lists each counted task’s play window, start, duration and overlapping measured work. Heap is CDP `JSHeapUsedSize` after `HeapProfiler.collectGarbage`. The closed-phone gate uses the larger reading from before the first raise and after the last play window. The open-phone reading comes from the second raise. The drip run is a 10-minute timed open sent through the raised phone's port. The 14-day log is made in the page at 1x: the player steps next to the house door and sleeps at 21:00 every night, which gives 101,920 ticks and 17 commands. Its load is `FarmRun.load` at the test's rate, reached through the facilitator's Load replay. Phone first open runs from the Raise phone click to the phone's zone heading and includes the 1.5 s mount delay in `src/phone-host.ts`.

The replay-load targets extrapolate the measured 30-day simulator cost after the hook (0.8-1.8 s, `research/tech.md` 1.2) to 14 days plus world physics; they are targets, not measurements. Node runs of the core under tsx on the shared workstation (2026-11-24 and 25, no browser) load that log in 1.9 s at 1x and a 14-day log without sleep (161,280 ticks) in 2.9 s. These are warm figures, the median of three loads in one process; the first load, which also compiles the code, takes 2.2 and 3.2 s. tsx keeps function names and the Vite build does not, so the loads were repeated from an esbuild bundle that approximates the production build (no `keepNames`, target `es2020`, minified): 2.0 and 3.0 s warm, 2.3 and 3.4 s for the first load. Under tsx the two logs took 3.4 and 5.3 s before the checkpoint stopped copying the simulator state and `advanceOsi` stopped repeating the `sim.advanceTo` it had just made (4.2), and 2.1 and 3.2 s after those two changes. The rest of the tsx gain came from removing a per-call closure in `World.nextBoundary`, whose name helper only tsx emits; the bundle loads in the same time with or without that closure. Every checkpoint hash stayed byte-identical. The same tsx runs time the step that dispatches the sleep at about 15 ms and a tick that hashes a checkpoint (every 600 ticks, so about two in the 60 s of play) at about 3 ms, the first one at 9 ms. Scaled linearly to 6x from the bundle, a projection rather than a browser measurement, the replay load comes to about 12 s warm and 14 s as a first load, against its 16 s gate. Scaled the same way from the tsx figures, the sleep jump (about 90 ms) plus the first checkpoint frame (about 53 ms) can give two long tasks, at the gate of two. A failed row fails `npm run test:e2e`, so the workflow never reaches `npm run verify` (11.3). Before the stack lands, the owner reads the measured 1x, 4x and 6x table and, for any row that still fails, decides between more speed and new targets taken from the 6x run. A physical low-end Android check (render-frame time with the phone open) is an owner-run step before any field pilot (section 15).

The binding performance gate runs locally at 6x under `osi-heavy` because hosted runner timings vary. Three hosted runs loaded the same replay log in 13.7, 16.2 and 19.7 s. They counted 6, 11 and 19 long tasks, with frame p95 of 17.4, 22.3 and 25.8 ms respectively. Local 6x runs recorded zero long tasks, 12.7–13.4 s for replay and 4.0–7.2 ms for frame p95. In the probe, “ours” is the time covered by simulation and render spans inside each long task, counting overlap once. The hosted job reports all timing metrics and still enforces the functional checks, heap limits and build.
