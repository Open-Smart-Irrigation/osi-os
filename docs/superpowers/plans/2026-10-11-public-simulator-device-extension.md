## Accepted implementation rulings

1. **One scenario, separate instrument representations — owner 7b-A, integration 7b-B.** `demo/model/forcing.ts` owns pure site-time weather, integrated physical rain and bounded water-response primitives. `device-forcing.test.ts` owns independent dimensional, interval-conservation, day/night, lag/recovery and clock-partition oracles. The device builders own native measurement representation and reporting cadence. Specialist ranges and example constants are illustrative; a single documented coherent selection is sufficient, without implementing every optional refinement. Missing area/efficiency never silently becomes 100 m²/85%: recorded liters remain available while a physical response needing unknown geometry stays unavailable. Capture valid geometry when delivery is applied, so subsequent edits cannot alter old wetting inputs. Getting this wrong double-counts water, changes a physical trajectory with reporting frequency, or presents invented metadata as measured fact.

2. **Depth edits remain metadata in this slice — owner 7b-B.** The fixed fictional installation gives each soil channel its response lag/attenuation and thermal depth. Saving a label alone is not an actual probe move. Preserve native normalized depth readback and source/chart labels without retroactive recomputation or an immediate tension jump. This is the selected resolution where specialist suggestions differed about applying edited depths to physical response. Separate deliberately constructed shallow/deep installation fixtures may test response attenuation and thermal lag. They do not imply that a native depth-label save physically relocates a sensor. No new relocation action is authorized. Incorrect coupling would make a label edit look like measured wetting or recalibration.

3. **Seed and Add behavior — owner 7b-B, visible proof 7b-C.** Public SDI12 Add creates the same usable manual TENSIOMARK scenario at 30 cm as the seed; the native Add form has no submitted probe profile to override. Preserve submitted identity/name/zone and any actual supported registration setting. All seven profiles remain changeable through native settings. New LSN50 keeps its established MOD9 default. Native MOD3 selection plus Chameleon enable must yield a distinct deterministic fictional attached array and a defined simulated known-calibration outcome through the ordinary sample/service path; it must not silently reuse E3's identity. Keep existing E3/E4 known/unlisted and WATERMARK fixtures. No hidden test action, external lookup, new production control or required user-supplied calibration identity is introduced. Without this ruling, newly added LSN50 could never exercise its visible Chameleon option once calibration is correctly required.

4. **Calibration and history exceptions — owner 7b-B.** Chameleon uses native `calibration_status` and independently tracks whether usable simulated calibration exists; an initial unknown array has no normalized tension, while a failed refresh cannot destroy valid cached data.
