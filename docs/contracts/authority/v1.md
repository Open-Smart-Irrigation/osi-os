# Edge/cloud authority v1

K1 fixes the authority rules for OSI OS 0.9. EB5a implements current-rights
checks, EB5b implements session revocation, EB6 implements edge Admin and grant
parity, and CL2 implements the cloud and installer boundaries. This document
specifies required behavior; the [consumer inventory](auth-consumers.md) records
what the pinned code actually does. K1 changes no running authorization code.

## Principals and roles

A gateway actor is an immutable `users.user_uuid` in one installation/gateway
context. Numeric `users.id` and username are lookup/display fields, not portable
identity. Cloud `User.userUuid`, cloud database id and gateway-local UUID are
different identifiers. CL2 resolves a cloud actor through the gateway's
`LinkedGatewayAccount.localUserUuid` and confirmed membership. Never substitute
the cloud UUID when that mapping is absent.

| Term | Stored representation today | Required meaning |
| --- | --- | --- |
| Gateway owner | Cloud gateway `Device.claimedBy`; linked edge identity is a separate mapping | Ownership of this gateway. Owning one zone/device does not make someone the gateway owner. A claimed gateway alone does not prove a local actor mapping (Q2). |
| Resource owner | Edge zone `user_id`, device `user_id`, plot `owner_user_uuid`; cloud mirrors | Ownership contributes that resource's scope. A grant widens scope without transferring ownership. |
| Admin | Edge `users.role = admin`; cloud `GatewayScope.Role.ADMIN` | Enabled gateway administrator. Can manage accounts/grants and gateway system controls. Resource writes still need ownership or a grant, except the stated unassigned-soil exception. |
| Member/writer | Edge `researcher`; cloud gateway `RESEARCHER` | Enabled member who can write owned/granted resources. “Member” is not a new stored role. An admin or viewer can also hold membership. |
| Viewer | Edge `viewer`; cloud gateway `VIEWER` | Enabled read-only member. Ownership or grants never turn this role into a writer. |
| Installer | No stored gateway role or installer entitlement at the inspected pins | Explicit authorization for this gateway's radio tools. Admin, ownership and a zone grant do not imply installer. Representation is Q1; deny tools when entitlement cannot be established. |
| Cloud account roles | `UserRole.USER`, `ADMIN`, `SUPER_ADMIN`, `FLEET_READER` | Separate platform roles. None automatically creates gateway membership, a grant, or installer entitlement. `FLEET_READER` is a restricted monitoring role. |
| Internal service/scheduler | Trusted execution context, not a login role | Only the narrowly identified internal operation. HTTP fields cannot select it. It never acts as a fallback for missing user identity. |

Unknown roles fail closed. Disabled/missing membership cannot exercise gateway
rights. Admin does not mean all-zone access: both edge `osi-scope-helper`
`assertFreshZoneAccess` and cloud `scopedaccess/GatewayScope.canManageZone`
combine a writer role with owned/granted scope. Cloud
`PhysicalCommandAuthorizer` also denies a zoneless valve rather than falling
back to its claimer on a scoped gateway.

## Rights and modes

`local_only`, `linked_online` and `linked_offline` describe connectivity and
credential mode. They do not change an enabled actor's authority. Local
administration and valid local/offline sign-in must work without a cloud call.
Cloud requests made while the edge is offline remain pending, not applied.

The resource grant rules below apply with scoped access enabled. The legacy
flag-off resource path retains owner-based selection until EB6 explicitly
migrates/enables scoped resource access. It must still enforce valid sessions,
disabled state and the owner/admin system boundary. The flag must never turn a
viewer/researcher into an administrator, including in `/api/me`.

| Action | Enabled gateway owner | Enabled gateway admin | Enabled researcher | Enabled viewer | Installer entitlement |
| --- | --- | --- | --- | --- | --- |
| Read account-wide edge data with scoped access on | Yes, with confirmed local identity | Yes | Yes | Yes | Adds no data entitlement |
| Cloud member zone list, history, analysis and CSV | Owned/permitted zones | Include granted zones | Include granted zones | Read permitted/granted zones | Adds no farm-data entitlement |
| Create a zone | With writer role | Yes | Yes | No | Adds no writer role |
| Change an existing zone, schedules or policy | Writer plus owned/granted zone | Owned/granted zone | Owned/granted zone | No | Adds no zone grant |
| Operate/cancel an assigned valve; retained STREGA actions | Writer plus owned/granted zone | Owned/granted zone | Owned/granted zone | No | Adds no actuation entitlement |
| Rename/configure device flags, Chameleon or soil settings; OSI remove/detach | Writer plus assigned-zone scope | Assigned-zone scope | Assigned-zone scope | No | Radio configuration follows separate rule |
| Configure unassigned supported soil sensor depth/calibration | Device owner with writer role | Yes | Device owner only | No | Adds no ownership |
| Manage users, roles, grants and local password reset | Admin role required | Yes | No | No | Adds no account-admin right |
| Reboot or fan | Yes, as this gateway's enabled mapped owner | Yes, without a zone grant | No | No, unless independently the gateway owner | Adds no system-command right |
| Write gateway system settings | Admin role required | Yes | No | No | Adds no settings-admin right |
| Radio observations, radio configuration/revisions and coverage/survey tools | Only if also installer | Only if also installer | Only if also installer | Only if also installer | Required, within gateway scope; disabled still denied |

Account-wide edge reads are the existing W1 behavior; the matrix does not
silently narrow them to write grants. Cloud parity must at least include the
member's granted zones in lists, channels, history and exports. Workspace,
saved-view and preference writes remain private to their author and do not
confer zone-write rights. Prediction-setting authority beyond the canonical
zone gate remains Q5. Existing delete-holder/last-admin safeguards survive.

### Granted-member valve parity (#451)

For an assigned valve, authorize the current enabled writer against the
current zone's ownership or active grant, on both origins. This applies to
bounded manual open, cancel, STREGA timed action, supported partial opening and
flushing, and the valve schedule/plan/settings routes. Chameleon and ordinary
device-setting parity uses the same assigned-zone boundary.

A successful shared scope check must reach the device even when
`devices.user_id` names somebody else. Replace owner-only downstream queries
with queries constrained by the already authorized immutable target and a
fresh apply-time check. Never remove an owner predicate as the entire fix.
After device reassignment, check the new zone, not the zone captured at click
or cloud issuance time. An outsider emits no frame and changes no record.

Capability, model, duration, interlock, queue-reservation and firmware gates
still apply. Normal STREGA opening is `OPEN_FOR_DURATION`; cancellation keeps
`handed_off`/uncertain outcomes. This contract grants no indefinite open and
no power to erase a radio record through the OSI Remove action.

### Admin and system controls

EB6 exposes user/grant administration in all three modes, including legacy
flag-off operation, after checking the account's actual current admin role.
The edge pin has grant POST/DELETE but no GET directory, and `/api/users`
returns accounts without assignments. EB6 must return existing active grants
with their assignment UUIDs, target resource UUIDs and member UUIDs so an
admin can inspect and revoke them after reload. An unavailable directory
must be shown as unavailable, never as an empty set of grants.
Preserve zero-user bootstrap, request-local credential isolation and the last
enabled-admin guard. Never promote an existing account on flag flip, link,
restart or migration as a way to make Admin work.

For `REBOOT` and `SET_FAN`, CL2 accepts only this gateway's current enabled
owner or confirmed enabled gateway admin, and EB5a checks the actor again
when applying. A zone grant, cloud `ADMIN`/`SUPER_ADMIN` alone or installer
entitlement is insufficient. Restrict the retained cloud system route to its
system-command allowlist, `REBOOT` and `SET_FAN`. The legacy valve door's retirement does
not remove admin fan/reboot. At the inspected pin,
`device/DeviceController.sendGatewayCommand` requires cloud `ADMIN` and
claimer/super-admin but does not admit an ordinary confirmed gateway admin;
the edge `Route Command` system branches do not reauthorize the actor.

### Installer boundary

CL2 and EB6 enforce installer-only radio tools in the backend and GUI. Cover
`GET /api/network/observations`, radio-configuration GET/PUT and revision
history, field-test survey/download tools and cloud
`GET /api/v1/network/observations`. Raw radio/history exports must not provide
an alternate door to the same installer-only data. Ordinary device GPS and
farm sensor history do not become installer-only merely because they use
location data. The current network module's device grants/admin tests are
insufficient. Q1 must settle the entitlement representation before activation.

## Evaluate current rights at apply time (EB5a)

Authenticate at entry, authorize at execution. Before a canonical mutation or
physical-effect reservation, on the write connection and under the relevant
writer/claim fence:

1. Resolve the trusted actor to a current account in this gateway context.
   Check enabled state and recognized role. For a local request, also validate
   the authenticated session's durable revocation state.
2. Resolve the current target, current zone/owner and active grants. Require
   the role/action class and scope in the matrix. Check installer entitlement
   for radio tools. Do not trust a token's role or a cached preflight result.
3. Apply the authorized change with its existing version/effect-key checks.
   Serialize any authority change that could race this boundary. If an async
   wait or dispatch delay releases the fence, validate again before effect.

Cloud transport authentication only establishes a trusted delivery path.
Cloud commands require an actor's gateway-local UUID bound to the command,
gateway and logical target. A client cannot supply a different actor in the
request body and have it treated as trusted. Missing/unknown actor is a
refusal, never owner/admin inference from the sync account. In particular,
cover `REGISTER_DEVICE` before ChirpStack provisioning, scoped-user/grant
commands, every valve schedule/plan/settings command, system commands,
rename and protected calibration/location commands. Carrying an actor UUID
without checking it is insufficient.

A deliberate authorization failure is terminal non-application with the
existing command ACK/result contract. Infrastructure failure reading rights
is retryable and produces no effect; it is not a permanent scope rejection.
The normalized fixture reasons map to existing command-specific codes during
EB5a/CL2; they do not introduce a new wire enum. Q6 covers missing actor fields
and capability rollout in the paired command schemas.

A replay of an already committed command returns its recorded outcome and
cannot emit a second effect, even after rights change. A new command requires
new current-rights authorization. Internal scheduled work retains its existing
trusted origin, current schedule/owner/scope safety checks and interlocks;
revoking a browser session neither invents nor cancels a schedule implicitly.

## Revoke every existing gateway session (#520 / EB5b)

A successful canonical disable, password reset/change or role change ends
**all** sessions for that gateway-local account, across browsers, tabs and
clients. Promotion also revokes. Re-enable never revives an old token. The
rule applies with either scoped-access flag value and in all connectivity
modes, including linked offline login.

The semantic contract is a durable per-account **session generation** (or an
equivalent durable session store with the same properties). Issuance binds a
session to immutable account identity, installation context, current
generation and finite expiry. A token's role/grants are never authoritative.
The generation and token format are not added to sync schemas by K1.
EB5b owns their encoding and an assigned, reviewed migration if needed.

The account mutation and revocation commit atomically. Success is returned
only after both persist. Consumers reject a mismatched/missing generation,
missing account, disabled account, invalid signature, invalid context or
expired token before private reads or effects. Use HTTP 401 for an ended or
invalid session so the existing GUI session-expiry boundary runs. Use 403 for
a valid session lacking action-class authority, and 404 for an out-of-scope
resource. An unavailable authority store fails closed with a service error
(503 for the normalized session contract), not a fabricated permissions result.

A session is expired when `now >= exp`; absent/zero/non-finite expiry is invalid.
Expiry uses an explicit clock/unit in the implementation; today's seven-day
local token uses milliseconds. Every current verifier is listed in the
inventory, including independent copies in modules and flag-off branches.
Replacing only `osi-scope-helper.verifyBearer` cannot complete EB5b.

“Immediately” linearizes at the edge's canonical account/revocation commit:
no request or queued local work may pass its next authorization/effect boundary
with a revoked session. An already transmitted frame cannot be unsent. An
in-flight private export must check again before releasing its response;
bytes already sent cannot be recovered. Do not describe a delayed reboot,
queued SQL update or buffered export as exempt because it authenticated first.

Credential verification and issuance must be fenced against a concurrent
reset: verifying an old password, then reading the new generation and signing
a new token, would defeat revocation. Session checks cannot use the 30-second
scope cache as a revocation grace period. Invalidate caches and pending loads
after commit; every verifier still checks durable session validity.

Grant revocation changes current resource rights immediately at apply time.
It need not end unrelated sessions under #520 unless EB5b deliberately chooses
a stricter policy. Rejected changes, unchanged role/disabled values and failed
transactions must not report successful revocation. An accepted password reset
always revokes, even if the chosen password is the same. Preserve last-admin refusal semantics.
Command replay must not increment the generation again.

### Credentials, upgrade and offline limits

Local `password_hash` reset and linked offline-verifier replacement are
different operations. `osi-local-password-reset.resetLocalPassword` correctly
refuses `auth_mode=server` with 409
`linked_account_password_reset_unsupported`; changing an unused local hash
must not be described as linked password recovery. Q4 covers the paired
linked-password change/reset path. Any accepted replacement of the effective
login credential must revoke sessions at its canonical edge commit.

New revocation-aware consumers reject pre-upgrade tokens that have no durable
binding; users sign in again. Preserve account UUIDs, passwords/verifiers,
ownership, grants and field history. Do not rotate the global signing key or
delete accounts as the implementation. A restart, cache reload or flag change
cannot reset generation or revalidate old tokens. EB5b must supply a rollback
policy that cannot re-enable an old verifier which accepts revoked tokens;
a binary rollback without that protection is unsupported.

Cloud-issued account changes are pending until the edge applies them. K1
requires immediate revocation at that application commit; it cannot deliver a
cloud change to a disconnected gateway instantly. Q3 asks whether the release
also needs a cloud-side session fence or a bounded offline credential policy.
Do not claim that scope-cache invalidation, token expiry or MQTT credential
rotation solves that propagation question.

## Fixtures and implementation acceptance

[MANIFEST.json](MANIFEST.json) lists the normalized fixtures. They contain no
real credentials, deployment identifiers, or signed usable tokens.
`fixtures/authorization.json` covers role/action/origin/mode decisions;
`fixtures/revocation.json` covers lifecycle/race outcomes.
`fixtures/auth-consumers.json` pins routes, node ids, module functions,
current checks and revocation reach. These inputs describe semantics, not a
new network payload. `allow` means only that the authority gate passes.

Run `node scripts/test-authority-contract.js` to check fixture consistency and
inventory coverage against the pinned edge Git object. It does not prove that
runtime consumers implement the decisions. Each implementer must replay the
relevant vectors against actual shipped function bodies/modules and provide
red/green evidence:

| Package | Required evidence |
| --- | --- |
| EB5a | Grant revoked, actor disabled or role changed after cloud issuance and after local preflight; changed device zone; missing actor; writer-wait race; transient DB failure; terminal denial emits no frame/write; completed replay emits no second effect. |
| EB5b | Every listed consumer class rejects every old session after disable/reset/role change, including promotion; both flags; re-enable/restart/cache reload; concurrent login/reset; in-flight load/export/queued effect; new login under current rights; legacy-token upgrade and safe rollback. |
| EB6 | Admin directory/grant listing, create/reload/revoke and password-reset refusal in every mode; granted-member edge/cloud valve parity; viewer/outsider denial; current scope at write; last-admin and credential-isolation tests. |
| CL2 | Confirmed gateway-admin and owner system commands; granted member refused system commands; installer backend/GUI boundary; granted zone lists/analysis/CSV; new actor mappings and capability/version compatibility; no direct confirmed-state cloud mutation. |

Cloud mirrors of these new authority fixtures require a paired CL2 change;
none was written into the read-only cloud checkout. Existing sync schema
mirrors remain unchanged.

## Open questions

- **Q1 — Installer representation (CL2/EB6):** What per-gateway role or
  entitlement stores installer authority, who grants/revokes it, and how is it
  mirrored to the edge? Neither role enum has it. Specify whether a read-only
  gateway viewer can independently hold this tool entitlement, and the exact
  survey/export endpoints it covers. Until confirmed, no implicit Admin or
  cloud SUPER_ADMIN bypass is permitted.
- **Q2 — Gateway owner mapping (CL2/EB2):** How does a claimed cloud gateway
  owner without a confirmed `localUserUuid` become an authenticated edge actor
  for reboot/fan, and where is gateway ownership recorded/verified locally?
  Existing single-owner resource columns are not proof. The decided owner/admin
  rule stands; missing proof must refuse pending an explicit paired mapping.
- **Q3 — Disconnected cloud revocation (CL2/EB5b):** Does a global cloud disable,
  reset or role change revoke gateway sessions before the corresponding edge
  account change applies? If yes, define delivery/acknowledgement, offline
  policy and failure semantics. An offline edge cannot observe an undelivered
  change. Preserve honest pending/applied status.
- **Q4 — Linked credential reset (EB5b/CL2):** Which cloud operation rotates the
  effective offline verifier, carries a credential/revocation revision, and
  prevents an older sync refresh from restoring it? How do password reset,
  ordinary change, unlink/relink and recovery interact with sessions? The local
  reset route remains a refusal for linked accounts until that path exists.
- **Q5 — Prediction-setting boundary (CL2, server #415):** Which retained
  prediction settings follow canonical zone-write permission, and are any
  owner/admin-only? K1 does not infer this from current inconsistent routes.
- **Q6 — Command actor rollout (EB5a/CL2, server #320):** Specify actor fields,
  trusted mapping and capability/version rollout for REGISTER_DEVICE, generic
  system and scoped-user/grant commands whose current envelopes lack or do not
  enforce an initiating actor. How are existing queued actorless commands
  settled during upgrade? They cannot be silently attributed to the owner.
