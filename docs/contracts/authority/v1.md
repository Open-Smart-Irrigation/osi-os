## Identity, roles and decided defaults

A gateway actor is `users.user_uuid` in an installation and gateway context.
Numeric local ids, usernames and cloud `User` identifiers are different
identifiers. Cloud admission resolves `LinkedGatewayAccount.localUserUuid`
through confirmed gateway membership. An absent mapping never substitutes a
zone owner, device claimer, transport account or global cloud UUID.

| Term | Baseline representation | Authority |
| --- | --- | --- |
| Gateway owner | Cloud gateway `Device.claimedBy`; local proof is not supplied by resource ownership | R3/Q2 requires confirmed enabled local pairing and durable gateway-ownership proof. An unpaired cloud owner is refused with a re-link hint; resource ownership is no substitute. |
| Resource owner | Zone/device `user_id`, plot `owner_user_uuid`, cloud mirrors | Contributes that resource's scope, without changing role. |
| Admin | Edge `admin`, cloud gateway `ADMIN` | Enabled gateway administrator. Accounts/grants and privileged administration; resource writes also require owned/granted scope. |
| Member/writer | Edge `researcher`, cloud gateway `RESEARCHER` | Enabled writer on owned/granted resources. “Member” is not a fourth stored role. |
| Viewer | Edge `viewer`, cloud gateway `VIEWER` | Farm reads; no farm mutation even when resource owner. A member/viewer role alone never authorizes radio tools or gateway system commands. |
| Installer (owner/admin activity) | Existing gateway owner/admin authority; no separate role or entitlement | R6/Q1 admits only the enabled paired gateway owner or enabled gateway admin, over the whole gateway's radio data. Ordinary members/viewers and cloud SUPER_ADMIN get no bypass. |
| Cloud account roles | `USER`, `ADMIN`, `SUPER_ADMIN`, `FLEET_READER` | Platform roles do not imply gateway membership, farm grants or radio-tool access. Fleet reader remains a restricted monitor. |
| Service principal | Authenticated, context-bound credential-management or sync execution | Only its typed operation; cannot act as a human-admin shortcut or produce valve authority. |
| Internal scheduler | Trusted internal execution origin | Existing enabled-policy/schedule and current scope/safety checks; never selected by HTTP body fields. |

Unknown roles and disabled/missing accounts fail closed. For ordinary scoped
writes, the edge combines `assertFreshZoneAccess` with `canMutate`:
the former checks enabled state and owned/granted scope, not writer role alone.
Cloud `GatewayScope.canManageZone` provides the corresponding conjunction.
The baseline cloud has shortcuts around this check; their deltas are explicit
in the next section.

`local_only`, `linked_online` and `linked_offline` change connectivity and
credential availability, not an authenticated actor's farm scope. Scoped mode
off retains explicit legacy owner selection for ordinary resources, while
current enabled state, role and session validity still apply. It never reports
a synthetic admin. Admin works without a cloud call once a stored enabled admin
exists. R2/Q8 stores an admin on fresh bootstrap and provides one recorded
original-bootstrap-only upgrade for eligible existing no-admin systems.
Operator recovery is the fallback when that original account is unavailable.

### First admin and one recorded upgrade (R2 / former Q8)

The pin's scoped bootstrap stores admin, its flag-off bootstrap stores researcher,
and flag-off `/api/me` invents admin. R2, decided on 20 Nov 2026, replaces the
synthetic presentation: fresh zero-user bootstrap stores a real admin in both
flags. Public bootstrap stays closed whenever any user exists.

For an existing installation with no enabled admin, run exactly one recorded
upgrade step, `bootstrap_admin_upgrade_v1`. Promote only the original bootstrap
account (the original first stored account), and only if it is enabled. Whenever
scoped access is off, that account already sees Admin through the synthetic
flag-off role; with scoped access on it does not. The step records the access the
account has while the flag is off. No other account is promoted.

The accepted existing-installation proof is the surviving `users.id=1` row,
with SQLite's durable `sqlite_sequence` entry `name='users'`, `seq >= 1` and
`seq >= MAX(users.id)`. `database/seed-blank.sql` declares `users.id INTEGER
PRIMARY KEY AUTOINCREMENT`; the empty seed and `auth-db-insert`'s flag-off
`INSERT ... WHERE NOT EXISTS (SELECT 1 FROM users)` create that first row before
any later account. AUTOINCREMENT retains that insertion ordering after deletion.
The marker is `sqlite_sequence(name='users').seq`, written by SQLite at INSERT;
it is an insertion high-water mark, not the identity of the bootstrap user.
The pinned flow writes **no separate bootstrap flag**: `auth-insert-complete`
only returns 201/success, and `edge_originated` is not a bootstrap marker.
Do not require a new historical flag that existing gateways never recorded.
The future `bootstrap_admin_upgrade_v1` receipt is not pre-upgrade proof.

Resolve that row to its existing `user_uuid`, preserving the account identity.
`users.created_at` is diagnostic, not a reliable ordering test on a Pi without
an RTC. The first-ever row id proves creation before the others even if a later
record has an earlier wall-clock timestamp. `MIN(remaining users.id)`, username,
current flag, role, resource ownership and global cloud identity are not proof.
If row 1 is absent, it cannot be replaced by a later surviving row. If the
AUTOINCREMENT insertion evidence is absent or has been rewritten,
operator recovery handles that exceptional installation; do not turn a missing
invented bootstrap flag into a general recovery requirement. A disabled original
also uses recovery. Operator recovery is only the fallback; with the surviving
enabled first account and this recorded proof, the one-time upgrade must promote
it, including installations that already have other users.

Commit role, session-generation advancement, audit entry and one-time receipt
atomically. Audit the target UUID and ruling date. A retry/restart reads the
receipt and never promotes again, even if the promoted account later becomes
disabled. A rollback records neither promotion nor receipt. Keep every account's
identity, credentials, grants and field history. Preserve last-enabled-admin
checks in subsequent administration.

This recorded original-bootstrap-only step is the explicit R2 exception to the
prior blanket ban on unattended promotion. There is no continuing startup,
login, flag-flip or relink promotion rule. Operator recovery remains the fallback
under the [account recovery runbook](../../operations/account-recovery-runbook.md);
never delete users to reopen bootstrap. EB6 owns the release note; EB5b/EB6
coordinate the assigned migration/receipt implementation. K1 assigns no number.

The 0.9 release notes must carry this line:

> The 0.9 upgrade records a one-time promotion of the original enabled bootstrap account to Admin on gateways with no enabled admin. Other accounts are not promoted; a missing or disabled bootstrap account requires operator recovery.

EB6 also lists active grants with assignment/member/resource UUIDs after reload;
unreadable grant state is not an empty list.

## Apply-time rights, services and K3 S7

Authenticate entry and recheck current rights at the canonical write/effect
boundary on the write connection and relevant writer/claim fence. For local
requests, recheck immutable session/account/context and durable generation;
then current role, current target zone/ownership and active grants. Async waits
or delayed dispatch that release that fence require another check. Cached
preflight markers are not authority.

Cloud ordinary commands carry a trusted gateway-local actor bound to command,
installation/link and target. Check that actor at apply, including REGISTER_DEVICE
before ChirpStack provisioning, account/grant mutations and each valve command.
Missing actor is a refusal. Deliberate denied authority is terminal non-application;
an unavailable authority store is retryable and produces no effect. Completed
command replay returns the recorded outcome without a second effect or a second
revocation generation increment. Upgrade refusal concerns unapplied cloud
pending-command records; preserve already committed outcomes and any physical
handoff/uncertainty evidence rather than fabricate non-application.

Two service boundaries are distinct from human administration:

| Operation | Admission and binding | Allowed effect |
| --- | --- | --- |
| `SYNC_LINKED_AUTH` | Authenticated credential-management issuer, authorized self-service password-change/recovery principal, exact current account/installation/gateway/link incarnation and ordered credential revision; `linked_auth_sync_v1` plus paired new-format support | Only atomic effective credential/account-binding/revocation update under the next section. Role or disabled-state mutation needs its separate privileged authorization; self-service cannot grant it. No farm/system privilege; no current-admin requirement for changing one's own credential. |
| `FORCE_EDGE_SYNC` | Authenticated service/transport principal bound to current gateway/link; `force_edge_sync_v1`. Local `/api/sync/force` requires gateway admin; linked-account cloud self-service may request its own credential/sync refresh after binding checks without farm-admin authority | Schedule existing sync work only. Every resulting mutation still has its own actor/credential gate. No implicit REGISTER_DEVICE, system or valve permission. |

### Decided actor protocol (R8b / former Q6)

The edge reports the new `authority_actor_v1` capability only when its actor and
session consumers enforce this contract. Deploy cloud acceptance/schema support
first. The cloud sends actor-bearing commands only to a gateway whose current,
authenticated installation/link report contains that capability. Existing
`linked_auth_sync_v1` or other command capabilities alone do not prove actor
support. Unsupported or stale reports never trigger an owner/legacy fallback.

Human commands carry `actor_kind: user` and the acting gateway-local
`actor_user_uuid`, bound to the command and logical target. Queued stops/pauses
retain that recorded original actor after rights loss or deletion. Preserve its
UUID for audit; never replace it with a zone owner or transport user.
`FORCE_EDGE_SYNC` and `SYNC_LINKED_AUTH` carry `actor_kind: system` and
`system_actor: gateway_transport`; their user-actor field is absent. This is a
system actor bound to the gateway's own non-human transport credential, not an
admin or a user grant. Credential self-service still needs its independently
authorized target-account/credential revision; a system actor cannot open valves,
change farm grants or issue arbitrary system commands.

Actorless queued cloud commands are settled as refused at upgrade, including
pre-K1 types. Persist the terminal rejection/ACK with an actor-missing reason,
no new effect and no attributed owner. Never reinterpret an actorless record as a
modern user's grant or authorize it under old claimer shortcuts. A completed
ledger replay keeps its recorded outcome and emits no second effect.

R8b keeps protected-command settlement: an applied write needs authoritative
ACK plus matching mirror convergence, in either order; definitive non-application
settles without a mirror. Neither acceptance nor a delivered stop proves physical
closure. REST remains the only command path; MQTT is telemetry/status/ACK only.

### Mapping K3 operate/manage to one grant

K1 has one write grant: an enabled admin/researcher owns or is granted the
current zone. Map K3 `operate` and `manage` to that same conjunction in 0.9.
They are action labels, not separate stored permissions. Manual open/cancel,
retained service actions and confirmed close override use it; so do schedule,
resend, settings, policy activation/change/pause and incident retry. K3's
operate-without-manage proposal grants no second entitlement through K1.
Policy/decisions reads follow W1 enabled-account reads on edge; cloud includes
permitted/granted zones. Retry reconciles an incident, never replays a past open.

Carry the same original local actor and logical gateway/zone/policy target
through cloud acceptance, durable pause intent, issuance and edge application.
Deleting the requester must not substitute the zone owner in either actor
binding or recorded attribution. Archive the original actor UUID if needed.

A provably undelivered create may be withdrawn and reported `create_withdrawn`.
An uncertain/delivered create requires a durable pause intent and honest pending
UI. `expected_policy_version: null` selects the current version of the bound
policy, never another policy. Pause is not physical closure.

R1 (20 Nov 2026) settles K3 S7: a previously authorized queued stop or pause
applies even after its requester loses the grant or is disabled/deleted. The
qualifying types are policy pause, valve cancel, and a queued confirmed
close-override whose effect is strictly CLOSE with no OPEN/return action. All
three use the trusted, original-actor-bound reduce-only continuation at issuance
and application. An unaccepted or newly submitted close still needs current
rights; confirmations, target binding and K3 handoff/evidence constraints remain.
The accepted stop remains bound to and recorded under the original actor, with
the revocation noted. Its trusted proof must permit only reduction of watering; it never opens,
re-enables, extends a run or changes an unrelated policy. Timed close with an
OPEN return is not a reduce-only continuation. A revoked browser session cannot
use this exception to submit a new request.

The authoritative ACK reports application and the UI shows the applied stop;
confirmed cloud state still waits for the matching mirror under the protected
fence. Fixtures assert pending-until-mirror, then paused/applied, while physical
CLOSED remains unproven. A fresh re-enable/open requires current authorization;
the stop continuation cannot carry that authority. After a terminal refusal,
a currently authorized actor may submit a new request with a new identity and
fresh acceptance proof; it does not rewrite the refused record or its actor.

## Session revocation and expiry (EB5b)

Canonical disable, accepted password reset/change, or role change revokes every
existing gateway session for that account. Promotion revokes too. Re-enable,
restart, cache reload and flag change cannot revive old tokens. The semantic
state is a durable session generation (or equivalent session store), bound to
immutable account, installation and link context with finite expiry. EB5b owns
encoding and assigned migration, not K1.

Commit account change and revocation atomically before reporting success.
Issuance must fence the password-check/reset race: verifying an old password
then minting at the new generation is forbidden. Unchanged role/disabled values,
replays and rejected/rolled-back writes do not claim a new revocation. An accepted
password reset always revokes even if the user chose the same password.

Session checks run before private reads and again before buffered private
response release or queued effects. No 30-second scope-cache grace period is
allowed; invalidate cached/pending scope loads after commit and validate durable
session state independently. Bytes already sent and frames already handed off
cannot be recalled. Grant removal independently takes effect at the next scoped
write boundary; it need not log out unrelated sessions.

HTTP 401 ends an invalid/revoked/context-mismatched/expired session. A valid
session without action-class rights gets 403; an out-of-scope resource gets 404.
Authority-store failure fails closed with service error, not invented denial or
empty scope. Cloud adapters retain command-specific rejection/result mappings;
normalized fixture decisions are not new wire enums.

R5, corrected by the CTO on **21 Nov 2026**, separates revocation from expiry.
Revocation is decided by generation only: a generation mismatch always denies,
whatever the clock says. Never compare a token's issued-at time against a
revocation timestamp; issue time cannot restore revoked authority.

Expiry uses `effective_now = max(current_clock, persisted_time_high_water)` and
rejects at `effective_now >= exp`, including equality. Missing/non-finite/zero
expiry is invalid. Persist the high-water mark across boot and session issuance;
clock rollback cannot extend or revive an expired token/session. A still-young
session remains usable while the clock is behind the mark if its generation and
binding are valid and its expiry is later than the effective time. The baseline
uses millisecond `iat`/`exp` with a seven-day lifetime.

A fresh local password login always succeeds for an enabled account with a
valid credential and context, including an offline boot at build time without
an RTC. Issue the new session with the current generation, timing its finite
lifetime from `effective_now` so it is usable immediately; persist that issuance
mark. Do not shorten expiry to the rolled-back wall clock, compare issue time
against revocation times, or refuse login merely because that clock is behind.
Credential/login races still require the current generation at issuance.
Fixtures execute offline fresh login and immediate use behind the mark, old
sessions denied after revocation at backward/equal/forward clock values, and
expired sessions remaining expired after rollback/restart.

Upgrade rejects old tokens missing the new durable binding and requires login.
Preserve account identities/history. Never use global signing-key rotation or
account deletion as this fix. EB5b must provide rollback protection against an
old verifier accepting revoked tokens; an unfenced binary downgrade is unsupported.

## Link incarnation and credential ordering (EB2 / CL2 / EB5b)

Browser revocation alone cannot prevent stale linked credentials from becoming
valid for a new login. The baseline cloud self-service password change already
publishes `SYNC_LINKED_AUTH` (`LinkedGatewaySyncService.changePassword` through
`AuthController`). Its v1 subject path repeats verifier version 1; its
installation-bound path increments the overloaded version from 2. Edge unlink
clears that version to zero, and `cs-reg-cloud-fn` can replace a differing verifier
at equal version. `LocalSyncService` link starts at version 1 or 2. These are
baseline deltas, not acceptable credential ordering.

Required durable state is an opaque, never-reused **link incarnation**, plus a
strictly ordered **credential revision within that incarnation**. Keep verifier
scheme (`gateway-v1` or `installation-v2`) separate from revision. Bind the tuple
to installation UUID, gateway identity, canonical cloud server/account identity
and immutable local user UUID. A transport token version is another axis.
Local-only accounts also have a durable local/tombstone incarnation; ordinary local login does not require an active cloud link. R8a/Q4 fixes the atomic semantics below; CL2/EB2/EB5b implement paired encoding and rollout. R8b/Q6 fixes the actor protocol.

EB2 captures the expected incarnation/context before remote link work. Finalize
link/relink by compare-and-set against that captured durable state. In one edge
transaction commit the new incarnation, active peer/link, local/cloud account
binding, effective verifier scheme/subject/revision, transport binding and session
revocation state. A stale completion cannot overwrite any part of that tuple.
Unlink commits a fresh tombstone incarnation and revocation in the same transaction;
never reuse the previous incarnation, even when linking the same accounts again.
A new link may start its own revision sequence; that does not reset an old lineage.
Recovery/restore must establish a new incarnation before accepting stale deliveries.

For credential deliveries, compare all bindings inside the transaction before
any account/verifier write:

| Input | Required outcome |
| --- | --- |
| Different/missing/tombstoned incarnation, account, gateway or installation | Refuse stale context; do not recreate link, repair a binding or write verifier |
| Lower revision in current incarnation | Stale refusal, no state change |
| Equal revision and identical effective credential/account mutation | Idempotent duplicate; no generation increment or freshness lie |
| Equal revision but different verifier, scheme or effective account state | Conflict, no write; never “refresh” a differing verifier at equal revision |
| Higher revision in exact active context | Atomically update verifier/account-binding fields and revocation generation; report applied only after commit |
| Transaction failure or stale finalize/refresh completion | Preserve prior link/account/verifier/revocation state; no partial up-to-date marker |

A credential self-service principal cannot change gateway role, disabled state or ownership. Any combined privileged account mutation needs independent account-command authorization and last-admin checks before the joint commit; failure preserves verifier and revocation state too.

Persist the canonical accepted credential/account mutation fingerprint with its revision. Compare duplicates with that record, not today's account fields; replay must not undo a later independent disable or role change. An already completed old-incarnation delivery may return its recorded old receipt without any effect on the current link; the cloud must not treat it as confirmation of the current incarnation.

Ordinary `/auth/refresh-sync` renewal changes only the transport token/expiry in
its captured current incarnation. It never changes verifier, sign-in mode, local
role, membership or session generation. Stale refresh replies are fenced even
if the username still matches. Within an incarnation, token issuance revision
or compare-and-set prevents an older refresh reply from overwriting a newer token. A real self-service password change/reset needs
its independently authorized ordered credential package; it does not require
human admin over the farm.

Linked login uses the current effective verifier: v1 password subject is bound
to the current gateway; v2 to the installation. Invalid/missing required subject
or inactive link fails closed with linked-login recovery guidance. Remove the
`server_password_hash` fallback from this path when subject resolution fails;
an unavailable subject must not downgrade authentication. Local password reset
continues to refuse `auth_mode=server` with 409
`linked_account_password_reset_unsupported`; changing an unused local hash is
not linked recovery. R8a/Q4 assigns EB2, CL2 and EB5b so neither linking nor reset
can cross the incarnation fence.

### Cloud fencing and offline login (R7 / former Q3)

Phil confirmed R7 on 20 Nov 2026. The cloud invalidates its own affected sessions
immediately on disable, password reset or role change. A disconnected gateway can still authenticate against its current
local/offline verifier until it reconnects and applies the pending revocation.
There is no offline-login deadline or authority lease: a farmer may obtain new
local sessions indefinitely while disconnected. Individual local tokens retain
normal finite expiry, and changes already committed locally still revoke at once.
Show pending honestly until the edge commit; do not claim that a cloud change
has already taken effect on an unreachable gateway.

The cloud status remains `pending` while disconnected and after reconnect until
the credential/revocation transaction commits at the edge, then becomes applied.
An attempted delivery while disconnected is deferred without changing credential,
account, generation or the pending status. Both v1 and v2 offline fixtures assert
old-credential login while offline, cloud fencing, reconnect, edge commit, and
only then rejection of the old local sessions/credential.

Deliver revocation through the gateway's own non-human transport credential.
Disabling a cloud user must neither disable that gateway principal nor prevent
its polling/refresh from receiving the revocation. The baseline human-subject
`JwtAuthenticationFilter` / `AuthController.refreshSync` stranding path is a delta
to remove. After reconnect, the independent gateway principal delivers the
ordered change; the canonical account/verifier/revocation commit ends the old
local sessions and denies new login under the revoked credential/account.
Transport failure remains visible and retryable; never revive a disabled human
principal to repair it. Fixtures separately assert immediate cloud fencing,
long-offline local login, successful gateway credential refresh with the human
disabled, and revocation at the eventual edge commit.
