# Requirements for a preserving image upgrade

A future image-upgrade project must preserve farm state on storage that the upgrade never rewrites. The current kept archive is insufficient: it is built in RAM and carried on a 64 MiB boot partition, while farm history can be hundreds of megabytes. A live file-copy archive can also lose committed SQLite writes. Until this project is qualified, use application deploy; an image is for a new device or deliberate reset.

1. On the old gateway, before capture or image writes, stop every relevant writer and inhibit restarts. Verify shutdown and SQLite checkpoint completion. Take verified `.backup` snapshots, including farm and radio stores, and record a manifest of the last committed application state. Preserve the token secret, installation identity, radio keys/configuration, journal media, sync/deploy witnesses, recovery backups and unknown durable `/data` content. Inventory configured path overrides too.
2. Prove the complete snapshot fits its destination before changing partitions. Transition existing gateways from the root overlay to a dedicated state partition with a verified backup off the device, capacity checks, interruption recovery and a documented operator rollback. Existing cards allocate 14 GiB to root; space for another partition cannot be assumed. Test changed partition tables and full-disk-write paths so sysupgrade never overwrites the state partition. After transfer, verify both structure and latest committed state. Old gateways need an explicit preparation delivery; a new image cannot add this retrospectively.
3. On the new image, validate the state partition, snapshot manifest and mount before services can write. Missing, unproven or incomplete state holds the application across reboot and manual starts. Never seed over a provisioned installation. Record each step and failure in a bounded durable file and serve a read-only recovery page.
4. Take a verified pre-migration backup, then invoke the same packaged migration corpus/runner and sanctioned ledger reconciliation used by application deploy. Preserve risk-class rules, writer exclusion, checksum/fingerprint checks and refusal on unproven ledgers. Do not change frozen boot DDL or invent a second migration implementation. Migration failure keeps the application down with the backup intact.
5. Only after migration succeeds, activate the matching image flows, helpers and GUI together. Never run kept old application code on the new image. Validate route coverage, retained login, closed additional self-registration, history, schedules and running valve expectations before releasing the hold. Keep W5's application-deploy switch/rollback contract working.

Qualification must cover head-70/head-79 fixtures, foreign-numbered/unproven ledgers, missing state, exhausted storage, failed migrations and interruptions at every transfer/mount/migration/activation boundary. Compare recent committed records, not only `integrity_check`. Require both maintained profiles, emulator evidence and representative storage power-cut tests before declaring field support.
