# Dispatch inventory: where the Go port may send, publish or write

Generated from `edge/contracts/dispatch-inventory.json` by `node edge/harness/verify-dispatch-inventory.js --write-markdown`. Do not edit this file by hand; edit the JSON and regenerate.

The Go port must never send, publish or write where the shipped Node-RED backend does not (CHARTER §1.4). Each entry below is one Go entry point and the effects it ends in. Each check is a test Node-RED makes before the effect, with its JavaScript line, the Go line that makes the same test, and a scenario step that exercises it on both backends.

## Rules

1. A change that adds or alters a Go path ending in an effect (a ChirpStack call, a cloud publish, an outbox row, a history row, a file write, a hold file) adds or updates its entry in `edge/contracts/dispatch-inventory.json` in the same pull request, before review. The verifier finds Go entry points that reach a sink with no entry and fails on them.

2. Reviewers check the diff against the inventory. For each entry the diff touches, they confirm that every check still has its Go line, that the Go line still makes the same test as the JavaScript line, and that the probe still covers it. They do not rediscover the boundaries from scratch.

3. A check with no Go line (`go: null`), no probe (`probe: null`) or `status: "open"` blocks the merge. `node edge/harness/verify-dispatch-inventory.js` exits 1 while any such check exists.

## How a reviewer uses it

- Run `node edge/harness/verify-dispatch-inventory.js`. A FAIL line names the entry, the check and the reason; "reaches ... but no inventory entry lists it" prints the Go call chain from the entry point to the sink.
- For each entry point in the diff, open its section below and read the JS and Go lines of every check side by side. A Go change that moves a check after a write, drops it or widens it is the finding.
- Replay the listed probe against the Go build (`node edge/harness/record.js --replay <oracle cassette> --out <dir> --backend-cmd <osi-edge>`). A red step on a check marked ok is a regression. Cloud payloads that are canonical JSON are compared after normalisation (lib/compare.js cloudPayload), so a same-form timestamp inside one is not a difference.
- Coverage is per entry point and effect class, not per sink site: an entry that already lists outbox covers every outbox site it reaches. `--scan` lists all sites, so a reviewer can see a new site under an existing class.
- Rows 11, 21 and 28 are ordering properties marked ok; their probes exercise the code path but cannot detect a reordering.
- Run `node edge/harness/verify-dispatch-inventory.js --scan` to see every entry point and the effects the static scan reaches from it.

## Keeping line numbers current

- Every reference is `path:line` or `path:start-end` plus an excerpt. The excerpt must occur exactly once in the file, on the first line of the range.
- When code above a reference moves, the verifier reports "excerpt is now at line N". Run `node edge/harness/verify-dispatch-inventory.js --fix-lines` to shift those references, check the diff of the JSON, then regenerate this file with `--write-markdown`.
- When the excerpt itself changes or stops being unique, edit the reference by hand: pick a new excerpt from the first line of the range that occurs once in the file.
- In `flows.json` a function node keeps its whole body on its `"func"` line, so a reference to a flow node is that line plus an excerpt from the body.
- When a fix lands for an open check, set its `go`, `goExcerpt` and `status: "ok"`, keep `finding` for the record, and regenerate this file. `node --test edge/harness/test/dispatch-inventory.test.js` fails if this file is stale.

## Effect sinks the verifier scans for

- ChirpStack DeviceService requests, keyed by the `api.<X>Request{` literal: Enqueue (enqueue), FlushDeviceQueue (flush), CreateDevice (device-create), CreateDeviceKeys and UpdateDeviceKeys (device-keys), UpdateDevice (device-update), DeleteDevice (device-delete). Get and List requests are reads. Any other request type fails the scan until it gets a class in `edge/harness/lib/dispatch-scan.js`.
- Cloud MQTT: `.cloud.Publish(`, `.cloud.PublishAwait(` and `cloudmqtt.Start(` (cloud-mqtt).
- Outbox: `INSERT INTO sync_outbox`, and any INSERT, UPDATE, DELETE or upsert on a table whose trigger in `database/seed-blank.sql` inserts into sync_outbox (outbox). History: writes to a table whose trigger inserts into sync_history_dirty_keys (history).
- Files: `os.WriteFile`, `os.CreateTemp`, `os.Rename`, `os.Remove` and similar (file-write; hold-file when the path names a recovery hold or lock).
- Expected absent: local MQTT publishes and hold-file writes. A Go site for either fails the scan.
- The call graph is name-based and over-approximates: a function name resolves to every Go function the call form allows. An entry that shares a handler with another route (GET schedules, login) therefore has an entry of its own whose checks show the branch that keeps it away from the effect.
- Shared entries (kind shared) cover a sink function many entry points reach, such as the auth secret write. The walk stops at a shared function and the shared entry carries its checks.
